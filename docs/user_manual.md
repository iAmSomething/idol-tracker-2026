# Operator and User Manual (운영자 및 사용자 매뉴얼)

## 1. 일반 사용자 매뉴얼 (User Manual)

Idol Tracker 2026 서비스는 누구나 웹 브라우저를 통해 K-Pop 아이돌의 최신 정보를 확인할 수 있도록 설계되었습니다.

### 1.1 메인 화면 활용
*   **월별 달력 보기:** 
    *   화면 좌측의 거대한 캘린더에서 해당 월의 컴백들을 일자별로 확인할 수 있습니다. 
    *   우측 상단의 `<- Prev` 및 `Next ->` 버튼을 눌러 과거나 미래의 컴백 일정을 넘겨볼 수 있습니다.
    *   'Group', 'Solo', 'Unit' 체크박스를 클릭하여 원하는 형태의 아티스트 컴백만 골라서 볼 수 있습니다.
*   **다가오는 컴백 (Upcoming):**
    *   화면 우측의 타임라인 영역에서 '오늘'을 기준으로 가장 빨리 다가오는 컴백들을 시간순으로 한눈에 파악할 수 있습니다.
*   **테마 전환:** 검색창 우측의 아이콘(달/해)을 눌러 시스템 라이트 모드와 다크 모드를 자유롭게 전환할 수 있습니다.

### 1.2 상세 정보 열람
*   **컴백 상세 조회:** 달력의 앨범 커버나 타임라인의 아이템을 클릭하면 컴백 상세 팝업이 뜹니다. 해당 앨범의 공식 뮤직비디오 영상을 즉시 시청하거나, 전체 트랙리스트 정보를 확인할 수 있습니다.
*   **아티스트 상세 조회:** 아티스트 이름을 클릭하면 별도의 상세 페이지로 이동합니다. 이곳에서 아티스트의 공식 인스타그램, 유튜브, 나무위키 등의 링크를 클릭해 외부 채널로 바로 넘어갈 수 있으며, 역대 모든 앨범 발매 기록을 조회할 수 있습니다.
*   **작곡가 탐색:** 트랙 상세 정보에서 밑줄 쳐진 작곡가의 이름을 클릭하면, 그 작곡가가 참여한 다른 아이돌들의 수록곡들을 모아서 팝업으로 볼 수 있습니다.

## 2. 운영자 매뉴얼 (Operator Manual)

본 매뉴얼은 데이터베이스를 관리하고 시스템을 유지보수하는 관리자(Developer/Admin)를 위한 가이드입니다. 관리자 작업은 프로젝트 루트 디렉토리의 `/scripts` 폴더 내 스크립트를 실행하여 수행합니다.

### 2.1 새로운 컴백/아티스트 데이터 스크래핑
주기적으로 외부 사이트를 스크래핑하여 새로운 정보를 가져오기 위해 다음 명령어를 실행합니다.

```bash
# 최신 발매 앨범 크롤링 메인 스크립트 실행
npm run crawl 
# 또는
npx tsx scripts/auto_crawler.ts
```
*   **기능:** Bugs 등에서 최신 앨범 리스트를 긁어오고, DB에 존재하지 않는 아티스트와 컴백 문서를 자동으로 생성합니다.

### 2.2 데이터 보완 (Backfilling)
부분적으로 누락된 데이터를 외부 검색을 통해 보완할 때 사용합니다.

```bash
# 뮤직비디오 URL 누락 건 조회 후 유튜브 검색을 통해 자동 연동
npx tsx scripts/fetch_official_mvs.ts

# 곡 상세 크레딧(작사/작곡)이 비어있는 트랙에 대해 보완
npx tsx scripts/fetch_track_credits.ts
```

### 2.3 데이터 클렌징 (Cleansing)
중복되거나 잘못된 데이터가 삽입된 경우 이를 병합하거나 삭제합니다.

```bash
# 중복된 트랙 삭제
npx tsx scripts/deduplicate_tracks.ts

# 동일한 아티스트가 여러 개의 ID로 쪼개진 경우, 하나의 ID로 병합
npx tsx scripts/migrate_artist_ids.ts
```

### 🚨 2.4 운영 시 주의사항 (Firebase 할당량 초과 방지)
Firestore 데이터베이스는 일일 무료 읽기 횟수(Read Quota)가 **50,000회**로 제한되어 있습니다 (Blaze 요금제로 업그레이드하기 전 기준).

*   **금지 사항:** 스크립트 작성 시 `getDocs(collection(db, "tracks"))` 처럼 **컬렉션 전체를 조회하는 코드를 반복해서 실행하지 마십시오**. `tracks` 문서는 수천 개에 달하기 때문에, 몇 번만 실행해도 5만 회 제한에 즉시 걸려 실서비스가 먹통("Quota Exceeded" 오류)이 될 수 있습니다.
*   **해결책 (모범 사례):**
    1.  특정 필드가 누락된 문서만 쿼리 (`where("composers", "==", null)`) 하거나,
    2.  로컬 캐싱(JSON 파일 덤프)을 만들어 전체 조회를 1번만 수행한 후, 메모리 내에서 연산을 완료하고, 변경된 문서들만 `updateDoc`을 통해 쓰는(Write) 방식으로 최적화해야 합니다.
